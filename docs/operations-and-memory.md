# 长期记忆与运营任务（功能使用说明）

本页讲两件已经上线、并且都在 **Mini App → 群组设置** 里的能力：**记忆透明**
（看本群长期事实、联网检索留档、派生摘要，并对单条事实纠错）与**运营任务**
（看六类任务的执行来源、周期计划与运行结果，并「预览 → 确认」手动执行）。

打开方式：最高管理员私聊机器人发 `/settings`，或群管理员从群内进入设置中心，
在「群组管理」里选中某个群，展开对应的分节。两处都**严格按群隔离**，只会
显示你有权限的那个群。

## 一、记忆透明

分三节，默认都只读：

| 分节 | 看什么 |
| --- | --- |
| 长期事实 | 本群提炼出的长期事实（身份、偏好、关系、事件、忌讳、技能、其他），带修订号 |
| 联网检索留档 | 本群检索类功能留下的检索记录（价格、新闻、事实、未知） |
| 群摘要 | 本群已有的派生摘要 |

它**不包含私聊内容，也不直接给来源原文**：正文要单独点开「来源原文」才会按
下面的规则去取。列表支持 `subject` / `category` 这类筛选与游标翻页，一次最多
50 条。

### 1. 事实纠错是这里唯一的写操作

对单条长期事实可以提交人工纠错，走的是**一次原子事务 + 修订号 CAS**：

- 请求必须带上你在列表里看到的 `expected_revision`。修订号对不上返回 **409**，
  页面提示「这条事实已经变化，请重看后再确认」——**不会**用你手上的旧文本覆盖
  别人刚改过的内容；
- 回包不可验证（例如写入结果未知）返回 **503**。这时**不自动重试、不补偿提交，
  也不承诺「没有任何效果」**，草稿留在页面上，由你显式重看后再决定；
- 纠错只改这条事实的正文，**来源原文仍然是原消息原文**，两者在页面上分开显示；
  人工纠错过的条目会标出来，不要把它当成来源原话。

### 2. 来源原文：取不到就明说，不猜

点开来源原文时，服务端会**先回本群现存归档里核验这条消息**，再决定给不给原文
和链接。结果是显式状态，不是「取不到就当没有」：

| 状态 | 含义 |
| --- | --- |
| 可展开 | 核验通过，给出脱敏 + 截断后的原文 |
| 来源已被确认删除 | 有真实删除证据，不给原文与链接 |
| 没有可展开的来源归档 | 这条事实本来就没有可核验的归档 |
| 当前不对外可见 | 例如被审核处理过 |
| 来源当前无法验证 | 核验本身失败（未知），**fail closed**，不给原文 |

「核验失败」和「归档缺失」是两件事：前者一律不给链接，不会因为查不到就退回
写入时存下的旧字段冒充现存证据。

**Topics（话题）链接**：只有调用方从一致归档行里读到的**可信** thread id 才会
拼进链接；thread 从正文、模型输出或用户输入里**推测**是不允许的。`General`
主题与旧数据（没有 thread）退回普通链接形状，**不伪造**。私有超级群的链接是
`t.me/c/…`，只有群成员能打开，页面会说明这一点。

## 二、运营任务

「运营任务」分节一次性展示六类任务的**名称、执行来源、周期计划、运行结果**，
并提供手动执行的「预览 → 确认」。分节默认折叠，首次展开才读一次（只读、不轮询、
不预取）；读过一次或失败过之后不再隐式重试，需要新的数据就手动刷新。

### 1. 六类任务

| 任务 | 手动执行时能做什么 | 可切换的自动执行来源 | 重试/重复边界 |
| --- | --- | --- | --- |
| 定时消息 | 按条目 ID 立即发送，一次最多 20 条 | 只有进程内 | 逐条发送；已成功的不再重发 |
| 群摘要 | `generate` 生成新摘要，或 `retry` 只重试失败队列 | 只有进程内 | `retry` 只覆盖失败队列，不动已成功的 |
| 签到提醒 | 指定**当天已到点且在当前生效时段内**的某个小时；留空＝当天已到点的最后一个生效时段 | 进程内 / 外部入口 | 同一 (群, 时段) 只发一次；来源切换**不补发**已经过去的时段 |
| 周活跃结算 | 结算**上一个完整自然周**（传别的周直接拒绝，不补发历史周） | 只有进程内 | 按 (用户, ISO 周) 幂等，重复跑不会重复加分 |
| 周报 | 生成统计天数（1–90，默认 7）的周报，业务周锚定**上一个完整自然周** | 只有进程内；周期计划**默认关闭** | 按 (目标, 周) 唯一，手动补跑与周期计划重叠也只发一条 |
| 商店到期处理 | 指定本批最多处理条数（1–200） | 进程内 / 外部入口 | 按权益逐条处理，重复跑不会重复扣 |

「可切换的自动执行来源」说的是**任务策略允许把自动执行切到哪一侧**，它
**不表示这个任务有没有命令行工具**：

- 六类任务都能在 Mini App 里手动执行；其中签到提醒、周活跃结算、周报、商店到期
  处理另有容器内命令（`python -m bot.tools.checkin_reminder` /
  `activity_award` / `weekly_report` / `shop_expire`）。既有部署继续用宿主 cron
  调这些命令的方式**保持原节奏**，见
  [定时任务](./fork-reference.md#定时任务内建计划与外部-cron)。
- 反过来，来源选项里**没有**「外部入口」的任务（定时消息、群摘要、周活跃结算、
  周报的自动执行）就是不能切给宿主 cron——只有进程内这一侧，不会因为升级就多出
  一个外部入口。

### 2. 预览 → 确认：两步，且确认只用一次

「预览」是真正只读的：**不写审计、不占位、不发消息、不调模型、不动积分**，
只算出这次会做什么、影响多少、有没有被守卫挡住。确认时要带上预览返回的**单次
令牌**（默认 120 秒过期，可配置 30–600 秒），并在写事务里**再复核一次**守卫；
令牌绑定参数，改一个参数就得重新预览。

### 3. 执行来源：只影响未来，不补历史

- 切换来源**必须两步确认**（预览一次、确认一次），并留下审计记录；
- 切换**只对下一个时段/锚点生效，不会补发切换之前的时段**；来源重新生效后，
  只有落在容差窗口内的时段才算「到点」；
- 程序**不读宿主的 crontab**：选「外部入口（宿主 cron）」时，外部登记情况对
  程序是**未知**的：页面写「外部宿主 cron 的登记情况未知」，这类任务的状态显示
  「外部计划未接入」，**不会**用占位日期或「当前时间 + 间隔」伪造下一次执行。
  请在宿主侧自己确认；
- 已有部署如果本来就用外部 cron 跑这些工具，**升级后保持原来的节奏**：升级
  不会因为「现在有进程内 runner 了」就替你补跑、补发或改你宿主上的计划。

签到提醒改造前的真实行为就是外部 cron，所以它的**默认来源是外部入口**；只有
在页面里显式切到「机器人进程内执行」并确认后，才由进程内的
`checkin_reminder_internal` 接管（每 60 秒看一次当前时段是否到点，容差窗口
1 小时，超出窗口的过时段**不补发**）。商店到期处理的进程内来源是
`shop-expiry-runner`（成功一轮 300 秒、失败后 900 秒重试，单轮 120 秒截止、
每批最多 200 条）。

### 4. 周期计划：目前只有周报，默认关闭

周报支持「周内某天 + 本地 HH:MM」的周期计划，由进程内 runner 触发
（每 30 秒看一次锚点）。要点：

- **默认关闭**。不显式开启并确认，就没有任何自动周报；
- 开启时算出的是**严格未来**的下一次时刻，所以开启计划**不会立刻补上一周**；
- 锚点只有在 **15 分钟容差窗口**内才执行。进程停机很久、或上一次入队一直失败，
  超过窗口的锚点属于「上一周期没跑上」，只能**跳过并把锚点推进到严格未来**——
  绝不因为重新上线就补发上一周；
- 页面显示的下一次时刻与 runner 用**同一个**判定函数，不会出现「页面说还有几秒、
  runner 却认为已经错过」；
- **没有自动排程的任务不会编造「下次时刻」**：周活跃结算是手动触发型，页面把它的
  「下次运行时间」标成「未知（仅手动）」；群摘要这类**事件驱动**的摘要同样给不出
  下一次时刻，也如实显示未知——算不出来就承认未知，不填一个看起来合理的数字。

## 三、群管理改动：怎么算「保存成功」

群规、关键词回复、定时消息（以及永久记忆）的改动走同一套保存语义，**改完不等于
已经生效**：

- **正常保存**：先在页面里编辑，改动进入草稿/待保存列表（「已加入待保存列表」
  「修改已记录，点击『保存全部』后生效」），点右上角「保存全部」才真正提交；
  全局配置在写之前还会先给出**保存前差异预览**，看过再确认；
- **保存成功要有明确回执**：服务端返回的文档必须**逐字段**与本次提交相容（条目 ID
  对得上、字段类型相符、布尔与列表字段齐全）才算这次改动被确认。字段缺失或互相
  矛盾都按**未确认**处理——拿到 2xx 不等于改成功了；
- **版本或对象冲突**：群设置被别的会话改过会提示「群设置已发生变化」，草稿保留；
  记录已被别处删除则提示「此条未由本次操作删除，可能已在别处删除」，本地按不可用
  处理，但**不算本次删除成功**；
- **未确认的写入不承诺「没有变化」，也不自动重试或自动重提**：提示「可能已生效，
  请重新查看后再决定是否重提」，**草稿与待删除项一律保留**，由你显式重新查看之后
  再决定。

一句话：改动要么拿到可核验的回执，要么明确停在未确认，界面不会替你猜。

## 四、运行结果与「未知」

一次手动执行会产生一次运行记录，逐项状态是：

| 状态 | 含义 | 能不能重试重发 |
| --- | --- | --- |
| 成功 | 出站成功并已记账 | 不重发 |
| 跳过 | 按业务规则本就不该发（例如未到点、守卫挡住） | 不重发 |
| 失败 | 明确失败，且能证明**没有出站** | 可以重试 |
| 未知 | 可能已经产生副作用（超时、回执丢失、记账未确认） | **不重发** |
| 已取消 | 执行前被取消 | 视业务键而定 |

「重试」只重跑**可以安全重发**的项；「未知」项即便人工点重试也**不会被重发**。
这一层不是靠内存里的标志位，而是一张**只追加的出站回执表**，键是稳定业务身份
（群 + 时段 / 条目 / 周 / 权益 + 版本），运营中心、常驻 runner 与命令行工具
**三个入口共用同一张表**：

- **先落保护再出站**：真实发送之前先在独立事务里抢下这条业务键的保护行；
- **未知禁止重发**：`已发送` 与 `未知` 都和出站前的保护态一样阻断重发，只有能
  证明「明确没有出站」的路径才会释放保护；
- **永不降级**：`已发送` 不会被后来的 `未知` 覆盖。

所以「发送成功但记账没写完」这种最危险的情况，换一个入口再跑也不会把同一条
消息发第二遍。

### 不确定的改动怎么收敛：对账

「未知」不是死结，但**只能按证据收敛**。对一次结果未知的运行可以点「对账」：
服务端回业务台账（积分流水、权益、出站回执）核对这次到底做成了什么，
**只把台账已经证明的结论写回**——证明成功就写成功，证明没做过就写没做过，
**证明不了就仍然是未知**，不会猜成成功或失败。已经确定结果的运行不需要、也不会
被重新对账。

这样，像「权益/积分已经改了但回执没收到」这种情况，既不会重复改一次，也不会因为
界面没显示成功就当成没发生过。

## 五、预算：没确认的调用不算免费

按群的可选功能预算护栏（默认关闭）在**真实网络调用之前**先预留，之后再用真实
用量结算：

- **发送前取消**（或被上游拒绝）会退回整笔未用预留；退款幂等，也不会把累计用量
  压成负数；
- **已经发出**的调用按**确认的真实用量**结算：预留只是上界，实际更小就退回差额；
- **结果未知**的调用（缺 `usage`、上游报未知、预留租约过期）保留**保守占用**并标
  「未知」，不按 0 计、也不退款——把未知当免费，等于每次超时都白送一次额度；
- 金额上限需要先配好单价，没配单价就不提供这个上限；
- **安全审核永远绕过**这层护栏。

## 六、常见误解

| 误解 | 实际行为 |
| --- | --- |
| 「机器人会自己排程，升级后自动帮我补上」 | 只有显式开启的周报周期计划才自动跑；且过窗口的锚点跳过不补发 |
| 「切到外部入口就一定会发」 | 外部登记情况对程序未知，得由你在宿主侧确认 cron 真的在调用 |
| 「点重试就会重发」 | 只有能证明「明确没出站」的失败项才可重发，未知项永远不重发 |
| 「来源原文取不到就是没删」 | 核验失败是**未知**，fail closed，不给原文也不给链接 |
| 「纠错之后来源原文也变了」 | 纠错只改事实正文，来源原文仍是原消息原文，两者分开显示 |
| 「事件驱动/摘要能预测下一次时间」 | 算不出来就给不出「下一次时刻」，**不编造** |
